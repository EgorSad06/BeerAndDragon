# ADR-002. Граница модуля-кандидата: пул декалей за контрактом `IObjectPool<T>`

## Контекст
- Дробовик за выстрел выпускает 12 дробин. Раньше каждая дробина делала `Instantiate` префаба дырки,
  а лишние дырки удалялись `Destroy` из статической очереди внутри `Weapon` (`Weapon.SpawnBulletHole`).
- Создание и уничтожение объектов в бою — кандидат на выделения памяти и паузы сборщика мусора
  (требования NFR-07, NFR-08). Но это **не измерялось**, поэтому объявлять пул узким местом нельзя.
- Чтобы исследовать это в следующих работах, нужен участок, которому можно подать **воспроизводимый вход**
  (одинаковое число и порядок постановок) и наблюдать отдельно от стрельбы, физики и ввода.
  Ещё нужна возможность подставить другую реализацию, не трогая код оружия.

## Рассмотренные варианты
| Вариант | Плюсы | Минусы |
|---|---|---|
| **A.** Оставить `Instantiate`/`Destroy` в `Weapon` | ничего не менять | логика размазана по `Weapon`; нельзя наблюдать отдельно; нет второй реализации для сравнения |
| **B.** Встроенный `UnityEngine.Pool.ObjectPool<T>` | готов, поддерживается Unity | другой контракт: `maxSize` ограничивает только свободные объекты, лишние **уничтожаются** при возврате, а число выданных не ограничено. Правила «не больше N дырок, при переполнении — переставить самую старую» в нём нет. Плюс зависимость от движка — нельзя собрать и проверить без Unity |
| **C.** Свой контракт `IObjectPool<T>` + две реализации + фабрика как точка сборки, потребитель `BulletHoles` | правило лимита и переиспользования — в одном месте; модуль не зависит от Unity (собирается `dotnet build`); реализации подменяются конфигурацией без изменения потребителя; есть прогон `-decalProbe N` | больше типов и косвенных вызовов (см. «Цена») |

## Решение
Вариант **C**.
- **Граница модуля-кандидата:** интерфейс `IObjectPool<T>` (модуль `ObjectPool`, без зависимостей от Unity).
- **Потребитель:** `BulletHoles`.
- **Точка сборки:** `Weapon.SetupBulletHoles` через `ObjectPoolFactory`, реализация выбирается параметром `decalPool` конфигурации.
- **Реализации:**
  - `BoundedPool<T>` — по умолчанию, без выделений после прогрева;
  - `LinkedPool<T>` — переиспользование за O(1), выделяет узел на каждую выдачу.
- **Воспроизводимый вход:** `-config <файл> -decalProbe N` — N постановок в фиксированные точки, без лучей и физики.
  В журнал пишутся реализация, счётчики пула, прирост кучи Mono и время.

## Последствия и цена
- **Типы:** +5 (`IObjectPool<T>`, `LinkedPool<T>`, `ObjectPoolFactory`, `PoolKind`, `PoolOverflow`), +2 в потребителе (`BulletHoles`, `BulletHoleProbe`).
- **Косвенные вызовы:**
  - каждый `Get`/`Release` идёт через интерфейс (виртуальный вызов, JIT не встраивает тело);
  - плюс вызовы делегатов `onGet`/`onRelease` на каждую операцию.
- **Память:**
  - `Prewarm(maxDecals)` держит 60 неактивных декалей постоянно, даже если игрок не стреляет;
  - у `LinkedPool` — ~48 Б на выдачу (по прогону `-decalProbe`).
- **Поведение:**
  - декали больше не прикрепляются к объекту, в который попали (лежат под общим корнем `[BulletHoles]`): на движущихся мишенях они не едут вместе с мишенью;
  - время жизни отсчитывается, только пока оружие активно (`Weapon.Update`).
- **Обязанности:**
  - обе реализации обязаны проходить общий набор `ObjectPoolContractTests`;
  - пул декалей используется только через `BulletHoles` — иначе порядок переиспользования разойдётся с очередью времени жизни.

## Способ проверки
1. `ObjectPoolContractTests` — один набор проверок контракта (штатные, граничные, ошибочные случаи, порядок ошибок)
   для обеих реализаций; `BulletHolesTests` — тот же потребитель с обеими реализациями.
2. Засеянные дефекты `pool-recycles-newest`, `pool-double-release`, `linked-recycles-newest` (`ci/mutations.json`)
   должны ронять тесты.
3. Прогон `-decalProbe 1000` с `ci/pz02/bounded-config.json` и `ci/pz02/linked-config.json`: одинаковые `created`,
   `active`, `recycled`. Различия по памяти и времени фиксируются как наблюдение, без выводов.
4. `python ci/check_module_map.py`: `ObjectPool` ни от чего не зависит, `BulletHoles` — только от `ObjectPool` и `Diagnostics`.
5. `dotnet build tools/pz02/PoolDoc`: модуль собирается без Unity, документация полная (CS1591 = ошибка).
