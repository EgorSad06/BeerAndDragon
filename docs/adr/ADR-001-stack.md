## Контекст
- **Тип продукта.** BeerAndDragon — однопользовательская 3D-игра (шутер от первого лица со скейтом),
  интерактивное приложение реального времени: 60+ кадров в секунду, физика, звук, UI.
- **Целевое окружение.** Windows 10/11 x64 — поставка игроку; Linux x64 без графики — автоматические проверки в CI.
- **Ограничения.** Один разработчик; учебный срок; бесплатные инструменты; сторонние 3D-модели, текстуры и звуки
  в форматах FBX/PNG/WAV; сборка и тесты должны выполняться в CI без ручных действий.
- **Опыт.** Есть опыт C# и редактора Unity; опыта C++ и низкоуровневых графических API нет.

## Решение
- **Язык:** C# 9 (профиль .NET Standard 2.1).
- **Движок и технологии:** Unity 6 (6000.3.0f1, LTS-ветка 6.x), конвейер рендера URP, физика PhysX (Rigidbody),
  UI на uGUI, ввод — Input Manager + Input System. Тесты — Unity Test Framework (NUnit).
- **Сборка игры:** скриптовый бэкенд **Mono**: C# компилируется в промежуточный язык (IL, `Assembly-CSharp.dll`),
  который при запуске выполняет среда Mono с JIT-компиляцией в машинный код; движок — нативная библиотека
  `UnityPlayer.dll`, её загружает исполняемый файл `BeerAndDragon.exe`.
- **Модель исполнения — игровой цикл, управляемый событиями движка, в одном главном потоке:**
  - каждый кадр движок опрашивает ввод и вызывает у компонентов `Update` / `LateUpdate`;
  - с фиксированным шагом 50 Гц вызывает `FixedUpdate` и выполняет шаг физики;
  - затем рисует кадр.

  Код игры — набор обработчиков этих событий плюс обработчики игровых событий (C#-события `Changed`, `Died`, `TrickAdded`).
  Внутри одного вызова обработка последовательная; собственных потоков и асинхронных обращений к сети нет.
  Запись журнала — синхронная, в файл.

## Причины и альтернатива
**Почему Unity + C#:**
- готовые физика, рендер, импорт FBX/PNG/WAV и редактор сцен — силы уходят на игровую логику, а не на движок;
- C# с управляемой памятью безопаснее для одного разработчика, чем C++;
- есть зрелая готовая автоматизация сборки и тестов в CI (GameCI, Docker-образы Unity);
- Unity Test Framework позволяет тестировать логику без запуска игры.

**Рассмотренная альтернатива — Godot 4 (GDScript/C#).** Открытый движок, бесплатный, лёгкий.
Отказ: меньше готовых решений для импорта сторонних ассетов в нашем наборе (скиннированные FBX, анимации);
поддержка C# в Godot 4 не позволяет экспорт во все платформы и менее зрелая; нет опыта работы с ним;
автоматизация CI беднее, чем GameCI для Unity.

Также рассматривался Unreal Engine 5 (C++/Blueprints): избыточен для учебного проекта,
сборка тяжелее и дольше, нужен C++.

## Последствия
**Что упрощается:**
- рендер, физика и импорт ассетов — готовые;
- сборка под Windows и Linux — одним вызовом `BuildPipeline.BuildPlayer`;
- версии зависимостей фиксируются в `Packages/packages-lock.json`, версия редактора — в `ProjectSettings/ProjectVersion.txt`.

**Ограничения:**
- **проприетарный движок:** нужна лицензия Unity (Personal) на каждой машине и в CI — секреты `UNITY_LICENSE/EMAIL/PASSWORD`;
- **версия редактора жёстко зафиксирована,** другая версия переимпортирует проект;
- **часть пути исполнения скрыта:**
  - JIT Mono — машинный код в файлах поставки не виден;
  - нативный `UnityPlayer.dll` поставляется без исходников;
- **сборка медленная** (импорт ассетов 5–15 мин, кэш `Library/`);
- **бинарные ассеты** требуют Git LFS.

**Обязанности:**
- держать Unity и пакеты на зафиксированных версиях;
- не использовать `UnityEditor` в коде игры — линтер, правило E001;
- проверять пользовательский ввод и конфигурацию явно, а не через `Debug.Assert`: assert вырезается из Release-сборки;
- логику, которую нужно тестировать, писать отдельно от `MonoBehaviour`:
  - `GameConfig.TryParse`, `BoundedPool`;
  - статические функции `Weapon`.
